## User Scenarios & Testing *(mandatory)*

### User Story 1 - 真源编译与上下文投影 (Priority: P1)

作为规则维护者，我希望把团队级规则、业务仓锁定版本与本仓规则及显式覆盖合并为可复现的发布包，并只把少量最高优先级指导放入代理常驻上下文，以便团队能扩展规则库而不挤占每次任务的上下文。

**Why this priority**: 这是规则权威来源和上下文成本控制的基础，其他检查与审计需要稳定、可识别的规则包。

**Independent Test**: 准备含中央规则、锁定依赖、本地规则和覆盖的样例仓，独立验证成功编译产物、同步指导块、覆盖环拒绝及确定性规则正反例回归结果。

**Acceptance Scenarios**:

1. **Given** 一套版本锁定的中央 Playbook、业务规则、本仓规则及无环显式 overrides，**When** 维护者编译规则，**Then** 系统校验配置 Schema 并产出只读规则包及其稳定哈希。
2. **Given** overrides 依赖图中存在环，**When** 维护者尝试发布，**Then** 发布被拒绝并报告构成环的规则链，且不替换已发布包。
3. **Given** 某条 deterministic 规则附有正例与反例 fixtures，**When** 编译或更新该规则，**Then** 两类 fixtures 均须通过，否则规则包不得发布并指出失败样例。
4. **Given** 人工 Pin 的红线不超过 3 条，**When** 生成代理项目指导，**Then** AGENTS.md 与 CLAUDE.md 中的托管块内容一致，且仅含所 Pin 红线和两步协议，总长度不超过 300 tokens；各领域技能文件按领域分别产出。
5. **Given** 规则数量从 50 增长到 500 条以上，**When** 用户加载常驻指导，**Then** 常驻文本长度保持固定上限，且未经按需检索不暴露完整规则库。

### User Story 2 - 多语言 Diff 检查、基线与影子回放 (Priority: P1)

作为 Go、Python、TypeScript 或 YAML/Infra 代码贡献者，我希望本地检查只关注本次新增或修改的行，并且只在相关语义信号出现时提示，以便快速得到可执行反馈而不被存量债务或无关规则打扰。

**Why this priority**: 开发者日常反馈必须足够快速、低噪音，才能让负面知识真正进入工作流。

**Independent Test**: 在含多语言文件、基线债务、豁免和不同规则类型的独立仓库中运行增量检查，并对选定历史窗口执行影子回放。

**Acceptance Scenarios**:

1. **Given** 仓库包含受支持语言文件且有增量 Git diff，**When** 开发者运行本地检查，**Then** 仅分析新增或修改行并匹配路径作用域与豁免，且在不超过 200ms 内返回结果。
2. **Given** 某违规位于已登记基线债务中且相关行未在本次 diff 中新增或修改，**When** 执行检查，**Then** 不将该存量问题报告为本次失败；若该行被修改，则重新评估。
3. **Given** diff 确定违反 deterministic 规则，**When** 执行检查，**Then** 检查阻断并给出至少一个符合规则的替代方案。
4. **Given** semantic 规则关联的代码信号未出现在 diff 中，**When** 执行检查，**Then** 该规则不触发、不输出提醒，也不消耗语义判断 Token；若信号出现，则明确标记为待语义判断而非确定性违规。
5. **Given** 指定过去 N 天历史及对应规则版本，**When** 用户启动影子回放，**Then** 系统报告逐规则触发次数、触发率和潜在误报样本，且不改变历史提交或阻断当前开发。

### User Story 3 - Agent 方案前路由、Hook 与防篡改凭据 (Priority: P1)

作为使用 AI 代理的工程师，我希望代理在行动前查询相关规则，并能为实际变更生成绑定规则包与 diff 的可验证遵守凭据，以便代理知道边界且审查者可以复核其声明。

**Why this priority**: 该故事把项目规则带入代理决策，并为代理参与的变更建立审计依据。

**Independent Test**: 在不连接治理服务的环境中，分别请求意图与路径咨询、规则搜索、四态判断、候选提案和高危路径提醒，验证返回结果与凭据绑定关系。

**Acceptance Scenarios**:

1. **Given** 代理提供意图和目标路径，**When** 请求 consult，**Then** 返回匹配规则及适用范围；若最佳相关性低于阈值，则诚实返回空命中，不编造规则。
2. **Given** 用户提供查询词，**When** 请求 search，**Then** 返回可定位的规则结果；当无匹配时返回空结果及查询状态。
3. **Given** 有待判断的 diff，**When** 代理请求 attest，**Then** 结果明确且仅使用 comply、not_triggered_in_logic、exempt、escalate 四种状态之一，并附带绑定规则包哈希及 diff 哈希的防篡改凭据；任一绑定内容变化后，凭据验证失败。
4. **Given** 代理通过 propose 提交一项新规则或修改建议，**When** 建议被接收，**Then** 其状态为 pending 候选草案，不影响当前有效规则，直至经人工评审并合入。
5. **Given** 代理即将操作已标记的高危领域，**When** 宿主触发操作前 Hook，**Then** 宿主在毫秒级收到对应风险提醒；Hook 不可用时，调用方可识别失败而不把提醒伪装为已送达。

### User Story 4 - CI 权威重算与人机混合审计 (Priority: P1)

作为 PR 审查者，我希望 CI 对 PR 变更独立重算规则结果，区分代理参与与纯人工提交，并用适合各类提交者的方式呈现高危语义风险，以便审计可靠且人工贡献者不会因代理专用流程被阻断。

**Why this priority**: 合并门禁是最终权威校验点，必须摆脱开发者本机状态并覆盖遗漏声明。

**Independent Test**: 对同一组人工 PR、代理 PR、伪造或失配凭据、缺漏语义声明和离线 CI 环境分别运行流水线，验证重算结果、门禁与评论内容。

**Acceptance Scenarios**:

1. **Given** PR diff 与仓库内规则包可用，**When** CI 执行检查，**Then** CI 独立重算并输出含文件与行位置的 SARIF 结果；执行不要求本地检查结果或远程中心服务。
2. **Given** PR 声明有 Agent 参与，**When** CI 收到凭据及语义触发声明，**Then** CI 校验凭据与规则包、diff 绑定关系及声明完整性；凭据无效或任何应有声明缺失时阻断合并。
3. **Given** PR 为纯人工提交，**When** CI 检查到高危语义规则，**Then** 不因缺少 Agent 表单或凭据而阻断，并在 PR 评论展示对应的高危语义自查卡片。
4. **Given** CI 检查完成，**When** 异步事件上报失败或超时，**Then** 该失败不改变 CI 门禁结论或阻塞合并。

### User Story 5 - 多语言零摩擦接入与分发 (Priority: P2)

作为团队成员，我希望首次接入时自动识别项目语言栈和本机 AI 宿主，并能快速检查配置健康度，以便在不同开发环境中用一致方式开始工作。

**Why this priority**: 低成本接入能让团队实际覆盖率提升，并减少个体配置漂移。

**Independent Test**: 在至少 Go、Python、TypeScript、YAML/Infra 样例仓和各类受支持宿主环境分别执行初始化与健康检查，并在干净环境验证分发包启动。

**Acceptance Scenarios**:

1. **Given** 新仓库含一种或多种受支持语言及可识别 AI 宿主，**When** 用户运行 init，**Then** 系统报告识别结果并生成对应项目配置；重复运行不会重复追加托管内容。
2. **Given** 规则包哈希、指导托管块、Hook 或 MCP 配置有一项不一致或不可用，**When** 用户运行 doctor，**Then** 系统逐项报告通过或失败并给出可操作的修复方向。
3. **Given** 用户在干净的受支持操作系统环境中安装发布包，**When** 启动本地工作流，**Then** 无需另行安装外部运行时即可完成 init、doctor 与本地检查。

### User Story 6 - 异步治理账本与健康度度量 (Priority: P3)

作为规则治理负责人，我希望异步汇总脱敏使用事件和规则健康度，以便发现低效规则、噪音源和可能的流程风险，同时不让遥测故障影响本地检查或 PR 合并。

**Why this priority**: 长期治理依赖可观测性，但不应成为团队采用核心工作流的前置条件。

**Independent Test**: 向独立账本提交模拟脱敏事件，验证七项度量、噪音率、死规约、高噪规约和不同规则生命周期提醒；关闭服务后重跑本地及 CI 核心流程。

**Acceptance Scenarios**:

1. **Given** 用户或团队已启用遥测，**When** 本地或 CI 产生可上报事件，**Then** 事件以异步方式发送且不包含源代码、提示词、密钥或个人身份信息；发送失败不阻断核心操作。
2. **Given** 账本收集了足够的事件样本，**When** 治理负责人查看健康度，**Then** 能查看 consult 援引率、警告精度、本地覆盖率、合入逃逸率、返工成本比、声明不符率及规则年龄分布这七项指标，并能查看各项的分子、分母和统计窗口。
3. **Given** 规则触发记录包含四态判断和人工覆写，**When** 计算规则噪音率，**Then** 对每条规则按 SNR = (not_triggered_in_logic + 人工覆写) / 总触发次数给出结果，并明确样本数；无触发样本时显示为无数据而非零噪音。
4. **Given** 规则连续 180 天没有命中，**When** 完成健康度汇总，**Then** 该规则被标记为疑似死规约并提示复审，不自动删除或停用。
5. **Given** 规则周均噪音率超过 70%，**When** 完成健康度汇总，**Then** 该规则被标记为高噪规约并提供触发与覆写数据以供调整。
6. **Given** 常规规则有 24 小时冷静期或事故热修复规则有 hotfix_expires_at，**When** 规则接近或超过其适用半衰期/到期点，**Then** 账本分别按常规冷静期和热修复到期时间发出提醒，且不混淆两种时限。

### Edge Cases

- 规则包的父版本、业务仓锁定版本不可获取或哈希不符时，编译不得悄悄回退到不同版本；须指出无法解析的来源或完整性错误。
- 两条作用域重叠的规则有互相矛盾的显式覆盖时，系统须报告冲突并要求配置明确优先关系；无明确关系时不得生成权威结果。
- Git diff 为空、包含重命名/删除/二进制文件、超出支持语言或仅涉及未分析区域时，检查结果须区分无变更、不可分析与未覆盖，不能报告为已完整检查。
- 豁免规则过期、路径模式无效或同时命中互斥豁免时，须显示豁免失效/冲突并继续按有效规则评估，不得静默放行。
- 影子回放遇到历史规则包不可用、浅克隆缺少历史或 N 天窗口无提交时，须报告回放范围与缺失原因，不将部分回放表述为完整结果。
- consult 低于阈值、规则库为空或检索不可用时须返回空/错误状态；Hook 或 MCP 不连通不得伪报成功。
- 基线记录本身有误、被删除或行被改写时须允许重新评估相关行，并保留基线变更的审计信息。
- 凭据对应的规则包或 diff 哈希任一不匹配、签名/校验内容损坏、重放到不同 PR 时均须拒绝凭据。
- 账本遇到零样本、迟到/重复事件或遥测中断时须标注数据新鲜度和样本规模，避免重复计数或把缺失解释为健康。
- 热修复到期字段缺失或格式无效时，该规则不可被当作有无限期豁免；须要求补正并记录治理提示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 规则维护者 MUST 能声明中央团队 Playbook 来源、业务仓锁定版本、本仓局部规则和显式 overrides；编译 MUST 校验 Schema、验证来源版本，并对 overrides 依赖图进行环检测。
- **FR-002**: 编译 MUST 在 overrides 成环或规则冲突未能确定优先关系时拒绝发布，并保留上一有效规则包。
- **FR-003**: 编译 MUST 产生只读规则包与稳定内容哈希；deterministic 规则 MUST 配有并通过至少一个正例和一个反例 fixture 才能发布。
- **FR-004**: 编译 MUST 同步维护 AGENTS.md 与 CLAUDE.md 中一致的托管内容；内容仅含最多三条人工 Pin 红线及两步协议，合计不超过 300 tokens；MUST 按领域分别生成 `.agents/skills/sker-*/SKILL.md`。
- **FR-005**: 代理常驻上下文大小 MUST 与规则总数解耦；规则库达到 500 条以上时仍只加载有界 Pin 与协议内容，具体规则按需提供。
- **FR-006**: 本地检查 MUST 支持 Go、Python、TypeScript、YAML/Infra，对增量 Git diff 仅分析新增/修改行，并支持路径作用域、豁免匹配与可审计的基线债务冻结。
- **FR-007**: 本地检查 MUST 对不超过 10,000 个变更行的增量 diff 在 200ms 内返回 deterministic 检查结果；存量基线问题仅在相关行变更后重新评估。
- **FR-008**: deterministic 违规 MUST 阻断并提供合规替代方案；semantic 规则 MUST 仅在其定义的 diff 代码信号出现时激活，未触发时不得提示或消耗语义判断 Token，并须明确结果的不确定性。
- **FR-009**: 影子回放 MUST 可对用户指定的过去 N 天历史计算逐规则触发率并呈现潜在误报样本，且不得改写历史或产生合并门禁。
- **FR-010**: MCP 能力 MUST 提供 consult、search、attest、propose；consult 支持意图与路径联合检索并在低于相关性阈值时返回空命中，attest 限定四态且凭据绑定规则包哈希和 diff 哈希，propose 只产生 pending 草案。
- **FR-011**: PreToolUse Hook MUST 在毫秒级将高危领域提醒注入宿主，并如实报告未送达状态。
- **FR-012**: CI MUST 能在无本地检查结果、无远程中心服务时基于 PR diff 独立重算，并输出带文件与行级位置的 SARIF 标注。
- **FR-013**: 对 Agent 参与 PR，CI MUST 验证凭据有效性及触发语义规则的声明完整性；缺漏或不匹配 MUST 阻断合并。纯人工 PR MUST 免除凭据/填表阻断，并在发现高危语义规则时提供评论自查卡片。
- **FR-014**: CI 事件上报 MUST 异步执行，失败或超时不得改变门禁结论或延迟合并结果。
- **FR-015**: init MUST 自动探测受支持语言栈与本机 AI 宿主并完成相应配置；doctor MUST 校验规则包哈希、托管块大小、Hook 与 MCP 连通性并输出逐项状态。
- **FR-016**: 发布物 MUST 支持目标操作系统的静态分发，用户无需安装外部运行时即可运行核心本地工作流。
- **FR-017**: 可选治理服务 MUST 异步接收脱敏事件；事件不得包含源代码、提示词、密钥或个人身份信息，且核心离线工作流不得依赖该服务。
- **FR-018**: 治理账本 MUST 展示七项核心度量及可解释的统计窗口和样本数；SNR MUST 按给定公式计算，零样本显示为无数据。
- **FR-019**: 治理账本 MUST 标记 180 天零命中的疑似死规约、周均噪音率高于 70% 的高噪规约，并区分常规 24 小时冷静期与含 `hotfix_expires_at` 的事故热修复到期提醒；账本不得自动删除、停用或使规则生效。
- **FR-020**: 人工审查 MUST 是规则变更生效的前置条件；Agent 仅可创建待评审提案，不可自行批准或激活规则。

### Key Entities

- **规则来源与锁定项**：中央 Playbook、业务仓版本锁、本仓规则及其版本与完整性标识。
- **规则与覆盖关系**：规则正文、领域、适用路径、deterministic/semantic 类型、代码触发信号、豁免、优先关系、正反 fixtures、冷静期或热修复到期时间。
- **规则包**：一组经校验并发布的规则、来源快照和稳定哈希，只读且可独立验证。
- **基线债务**：已有问题的定位与例外状态，用于阻止存量问题扩大，并在相关行修改时重新评估。
- **检查结果与凭据**：规则命中、位置、四态结果、规则包哈希、diff 哈希及完整性证明。
- **代理提案**：待人工评审的规则新增或变更建议及其状态。
- **治理事件与度量**：脱敏事件、统计窗口、分子分母、规则噪音率、年龄和生命周期提醒。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 规则库达到至少 500 条时，代理常驻指导仍不超过 300 tokens，且规则增加不导致常驻指导长度随规则数增长。
- **SC-002**: 对最多 10,000 个变更行的本地增量检查，95% 的运行在 200ms 内完成；未触发 semantic 信号的运行产生零语义提醒和零语义 Token 消耗。
- **SC-003**: 所有可发布的 deterministic 规则在发布时均有通过的正例与反例回归样例；人为注入的覆盖环在每次发布尝试中均被拒绝。
- **SC-004**: 在 20 人目标团队试用验收中，六类故事各自的独立验收场景均可完成，且核心本地检查与 CI 在断网条件下仍成功完成。
- **SC-005**: 每一条 Agent PR 的有效凭据均能验证绑定到该 PR 的规则包和 diff；伪造、缺失或绑定不符的凭据/必需声明均被 CI 阻断。
- **SC-006**: 纯人工 PR 不会因缺少 Agent 专用凭据被阻断；命中高危语义规则时 100% 展示自查卡片。
- **SC-007**: 账本能以配置的统计窗口复算七项核心度量与规则 SNR；180 天零命中和周均噪音率 >70% 的规则均被识别并进入复审提醒。
- **SC-008**: 关闭或不可达治理服务时，本地检查、consult 与 CI 的完成率不受影响；异步上报故障不改变门禁结果。

## Assumptions

- 首发支持范围固定为 Go、Python、TypeScript 与 YAML/Infra；其他语言在后续版本评估。
- 目标团队约 20 人，规则库容量验收下限为 500 条；上下文成本以人工 Pin 和协议的 token 数为准。
- 200ms 指在目标支持环境的参考仓库中，对最多 10,000 个新增/修改行的本地增量检查的 p95 时限；基准环境在计划阶段进一步固定。
- 路径作用域、豁免、semantic 触发信号与相关性阈值均由可审查的规则元数据定义；阈值在规则库/产品配置中可被团队维护。
- 遥测为显式可配置能力；用户可关闭遥测，核心工作流不得因此降级。
- 所有规则更新需经 Git 中的人工审查与合入后生效；提案不具备发布权限。
- 本规约中的治理度量需呈现样本数与统计窗口；“警告精度”“返工成本比”等计算口径由团队治理政策在实施计划前确定，并保持可复算。
